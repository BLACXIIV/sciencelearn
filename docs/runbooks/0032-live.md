# Runbook — apply `0032_builder` to production

Verified on a throwaway dev project (same Postgres engine as live):
migrations 0001–0032 apply clean to an empty DB, and the test suite at
`supabase/dev_tests/0032_builder_test.sql` passes 14/14 twice (before and
after a rollback + re-apply cycle).

The file that must be applied is exactly:

`supabase/migrations/0032_builder.sql`
**sha256: `4C6D4898F3D54E2E48BE7A348E01B0EA227E0715253547D7AC5F537CDA87F0CB`**

Check before running: `Get-FileHash supabase\migrations\0032_builder.sql`
must print that hash. If it does not, stop — the file changed since
verification.

## 1. BEFORE — snapshot the position data

The position repair renumbers `assessment_parts.position` and
`questions.position`. It is a repair, not schema, and cannot be undone by
the rollback script — the only undo is restoring the old values.

In the Supabase dashboard **Table editor** on the LIVE project:

- Export `public.questions` as CSV (all rows).
- Export `public.assessment_parts` as CSV (all rows).

Keep both CSVs somewhere outside the repo.

## 2. APPLY — SQL editor only

Do **not** use `supabase db push` — live migration history is not trusted
(migrations were hand-applied). Applying via db push would try to replay
files the table thinks are missing.

- Dashboard → **SQL editor** → new query.
- Paste the **entire** contents of `supabase/migrations/0032_builder.sql`.
- Run once. Expected: "Success. No rows returned" — no errors.

## 3. VERIFY — run each in the SQL editor

```sql
-- a) all three objects exist
select proname from pg_proc
where proname in ('preview_questions',
                  'guard_assessment_publish',
                  'guard_assessment_delete');
-- expect: 3 rows
```

```sql
-- b) no duplicate positions remain (parts)
select assessment_id, position, count(*)
from assessment_parts
group by 1, 2 having count(*) > 1;
-- expect: 0 rows
```

```sql
-- c) no duplicate positions remain (questions, per assessment+part)
select assessment_id, part_id, position, count(*)
from questions
group by 1, 2, 3 having count(*) > 1;
-- expect: 0 rows
```

```sql
-- d) execute grants: authenticated yes, anon/public no
select
  has_function_privilege('authenticated',
    'preview_questions(uuid)', 'execute') as authenticated_ok,
  has_function_privilege('anon',
    'preview_questions(uuid)', 'execute') as anon_denied,
  has_function_privilege('public',
    'preview_questions(uuid)', 'execute') as public_denied;
-- expect: authenticated_ok = true, anon_denied = false, public_denied = false
```

## 4. ROLLBACK — only if something misbehaves

Paste and run `supabase/rollbacks/0032_builder_rollback.sql` in the SQL
editor. It drops the two triggers, the two guard functions, and revokes +
drops `preview_questions`.

**The position repair is NOT reverted** — dense positions are safe for old
clients. To restore original positions, re-apply the `position` values from
the CSV snapshots taken in step 1.

## 5. DEPLOY ORDER

1. **Migration first.** The app code that calls `preview_questions` and
   relies on the guards degrades gracefully until this lands (clear
   "not available yet" states, no crashes), so shipping code early is safe —
   but preview/guards only start working once this SQL is applied.
2. App code after: web build + Flutter release containing the Step-2
   changes.

Rollback order (if needed): app code can stay deployed — it falls back to
the "not available" states when the objects are gone.
